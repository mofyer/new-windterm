# P1 本地终端启动后执行命令：实施前语义与验证预案

日期：2026-11-07。只读核对基线：`p1/integration` 的 `c3b3a68`。第四批会话环境变量与 locale 已实现，但尚未验收，也未获 main 合并批准。

本文只定义用户可见语义、输入门控与验证方法，**没有实现任何代码，也没有运行任何新验证**。本文不改变功能矩阵或台账状态，不新增、删除或改写功能 ID。下文的“启动命令”指 WindTerm 2.7.0 字符串 “Execute command after start”（中文语言包为“启动后执行命令”）。

## 1. 范围与功能 ID

- **对应 ID：T34「本地 Shell 会话启动参数」中的“启动后执行命令”子项。** 冻结验收原文要求：“命令失败……有明确反馈；启动命令显式配置，重连或恢复时不自动重放此前输入；各平台本地 shell 分别核对”。T34 的目录子项由第二批交付，环境变量与 locale 子项在第四批；本切片完成也不代表 T34 整项完成。
- **相关但不在本切片**：C05「SSH 认证后自动执行」（P2）、S16「断开/重连会话」、G41 触发器中的“运行命令/发送文本”动作。它们以后可以复用本文的“一次发送”与状态语义，但各自单独验收。
- 只覆盖本地 PTY 会话（`mode: "pty"`）。SSH、Telnet/Raw TCP 与演示会话不加入口。
- **不交付**：持久化配置、多条命令脚本、按输出匹配后自动应答（属 G41）、延迟发送、自定义 argv，以及 WSL/Git Bash/Cygwin/Clink。

## 2. 现状（`c3b3a68` 代码事实）

| 位置 | 当前行为 | 对本切片的含义 |
| --- | --- | --- |
| `apps/desktop/src/main.ts` `queueInput` | 有 `ptyId` 时交给 `InputQueue`。没有 `ptyId` 时，只有来源为 `reply` 的本地 PTY 输入进入 early FIFO（上限 4096 字节）；用户按键、粘贴、`insertText` 和 `onBinary` 直接丢弃 | 启动命令不能借用 early FIFO，也不能伪装成 `reply` |

## 4. 用户可见语义

### 4.1 配置位置

- 在「本地终端启动选项」对话框（`#local-dialog`）中，启动目录之后、环境变量之前，增加一个可选字段「启动后执行命令」。留空表示不发送。
- 「本地终端」一键入口和留空的表单保持现有行为：不发送命令，IPC 序列不变。
- 建议说明文案：“Shell 启动后发送一次，相当于输入这一行再按回车，按所选 Shell 的语法解释。应用不等待提示符，也不判断命令是否执行或成功。配置只保存在本次会话的内存中。”
- 配置与 cwd/Shell/env/locale 一起深复制为会话快照。之后修改表单，不影响已有会话。

### 4.2 发送时机与次数

- **时机**：`pty_open` 成功返回，且会话没有结束、关闭或销毁；early 协议回复交给输入队列之后，立即发送。不等待提示符、首次输出、CPR、固定延时或用户操作。
- **内容**：命令原文的 UTF-8 字节，末尾加一个 CR（`\r`，即回车键）。不加 LF，不包 bracketed paste，不做转义、展开或引号处理。
- **次数**：每个成功打开的会话，**最多交给输入队列一次**。以下事件都不会再次发送：resize、切换标签、分屏、聚焦与失焦、对话框开关、ACK 超时、输入队列满后的等待。没有自动重试。
- **窗口重新加载**：既有 `reload_owner` 会关闭该窗口的全部会话，前端状态从零开始，配置也不持久化，所以不会恢复或补发。

### 4.3 重新打开

推荐方案（Q1 待用户确认）：

- 「重新打开」创建新会话，继承原配置，包括启动命令，并在新会话中按 4.2 再发送一次。旧会话不补发。
- 原会话带启动命令时，重开按钮的可访问描述和状态说明写明“将再次发送启动命令”。如果不想再次执行，可以先用「修改启动选项」清空该字段再启动。
- 连点两次重开只新建一个会话（沿用第一批的同步激活），所以仍是最多一次。

### 4.4 启动失败、提前退出与写入失败

| 情形 | 发送结果 | 用户看到的状态（不含命令内容） |
| --- | --- | --- |
| `pty_open` 被拒绝（目录、Shell、环境校验或系统错误） | 未发送 | “启动失败：<后端错误> · 启动命令未发送”；可修改启动选项，在新会话中重试 |
| `pty_open` 返回前已收到 exit | 未发送 | “已退出 · code N · 启动命令未发送” |
| 启动过程中关闭了标签或窗口 | 未发送 | 标签关闭；晚到的 ID 按既有逻辑关闭 |
| 已交给输入队列，但写入请求发出前会话结束，队列被清空 | 未发送 | “启动命令未发送（会话已结束）” |
| 写入请求被后端拒绝，或写入进行中会话结束 | 未确认 | “启动命令发送未确认：<错误>”；不重试；会话若仍在运行，可继续手动输入 |
| 后端已接收 | 已提交 | “本机 shell 已启动 · 启动命令已提交”。之后 Shell 退出（包括命令本身就是 `exit`），照常显示退出码，仍标“已提交” |

- 发送状态是单独的字段，与生命周期状态拼接显示。exit、错误和 resize 失败都不会覆盖它。文案、toast、标题和读屏播报都不包含命令内容。
- 不向 xterm 写入应用提示。本地插入的文本会和 Shell 输出交错，还可能改变 ConPTY 启动 CPR 报告的光标位置。

### 4.5 不承诺的内容

- “已提交”只表示命令字节已进入本机 PTY 输入队列（即 `pty_write` 成功的含义）。它不表示已写入 PTY、Shell 已读取、命令已执行或执行成功。
- **不保证 Shell 已就绪。** 命令通常在 Shell 初始化完成前到达，作为预输入（type-ahead）由终端驱动或 conhost 暂存。可能出现的情况：
  - 回显重复一次，或处理延迟；
  - 个别 Shell 初始化时丢弃或重排预输入（尚未实测）。
- **不判断命令成功或失败**，不解析输出或退出码。命令失败时，用户看到的反馈就是 Shell 自己的输出和退出码。
  - 本文把 T34 的“命令失败……有明确反馈”理解为：应用明确报告发送状态，并保留 Shell 自身的错误输出。这一理解须用户确认（Q2）。
- 命令若读取标准输入（如 `ssh`、`python`、`read`），之后用户键入的内容会交给该程序。这是正常的终端行为。
- 不消除 Windows Job 初始化竞态，也不改变 Windows PowerShell 首次 cmdlet 的慢路径（见第 6 节）。

## 5. 输入来源门控、排序与“恰好一次”

### 5.1 三类来源的隔离规则

| 来源 | 会话 ID 到达前 | ID 到达的同步代码段 | ID 到达后 |
| --- | --- | --- | --- |
| CPR 等协议回复（`onReply` 标记） | 进入 early FIFO（不超过 4096 字节） | `flushEarlyInput` 按序交给 `InputQueue` | 直接进入 `InputQueue` |
| 启动命令 | 不生成字节，不进 early FIFO | 紧跟 early flush，`push` 一次 | 不再出现 |
| 用户输入（按键、粘贴、`insertText`、二进制、拖放） | 丢弃（保持现状） | 不可能插入（JS 单线程，同步代码段中间不会处理事件） | 直接进入 `InputQueue`，排在命令之后 |

排序结论：

- 赋值 `s.ptyId`、`flushEarlyInput` 与命令 `push` 在同一个同步代码段完成，所以输入队列顺序固定为：**ID 到达前已产生的协议回复 → 启动命令 → 此后的回复与用户输入**。
- 如果 `ESC[6n` 在 ID 到达后才收到，它的回复会排在命令之后。两种顺序都可能出现，必须分别验证（8.2）。
- `InputQueue` 同一时刻只有一个写请求。命令最多 1001 字节（含 CR），只占一块，不会被其他输入切开。
- 不用 `disableStdin`，不暂停 xterm 输入，也不按提示符、首次输出或固定延时放行。

### 5.2 一次性状态机

每个 Session 有一个一次性字段 `startup`，取值为 `none | pending | queued | submitted | not-sent | unconfirmed`。状态只能前进，不能回到 `pending` 或 `queued`。

- 创建时：配置了命令为 `pending`，否则为 `none`。
- `openPty` 成功且会话存活：`push` 成功 → `queued`；`push` 被拒（理论上只有 16 MiB 积压上限）→ `not-sent`。
- 命令所在块：
  - 写入成功 → `submitted`；
  - 写入请求发出前被 `clear()` 丢弃 → `not-sent`；
  - 写入请求被拒，或请求在途时会话结束、队列被清空 → `unconfirmed`。
- `openPty` 失败、ID 到达前已退出、关闭或销毁 → `not-sent`。

实现要求：

- `InputQueue` 要为单次 `push` 提供结果回调或等价机制，只用于启动命令；普通输入的重试与丢弃规则不变。
- 队列满时重发同一块不违背“一次”：后端已明确表示没有接收这一块。
- 结果回调必须覆盖一条静默路径：`#send` 在队列满后的等待中发现队列已被清空或会话不可写时，直接返回，不抛错，`#pump` 的 catch 不会触发（`input-queue.ts` `#send`）。这时最后一次尝试已被后端明确拒绝，应记为 `not-sent`。
- 兜底：会话退出、启动失败、关闭或销毁时，若 `startup` 仍为 `queued`，按当时是否有写请求在途，转为 `unconfirmed` 或 `not-sent`。不依赖 `InputQueue` 一定回调。

“恰好一次”在两个层面的含义：

- **产品承诺**：最多提交一次，并明确报告已提交、未发送或未确认。
- **验证要求**：对已验证的 Shell 与平台，测试条件下实际副作用次数为 1（第 8 节）。

### 5.3 实现位置

推荐方案 A。这是技术选择，不需要用户决定；审查可以改。

- **A（推荐）：前端在上述同步代码段，经既有 `pty_write` 发送。**
  - 优点：
    - 不新增 Tauri 命令，也不新增 `pty_open` 参数，ACL 不变；
    - 命令值不经过 Rust 参数反序列化；
    - 当 `ESC[6n` 早于 ID 到达时（现有 early FIFO 正是为这种情况设计的），顺序与现有原生场景“启动并读回输出后才键入”的路径一致。
  - 约束：
    - 命令存放在 Session 的独立字段，或在调用 `pty_open` 时显式排除，不能经 `...s.launch` 展开传给 Rust；
    - 快照与深复制要覆盖新字段。
- **B（备选）：`pty_open` 增加可选参数，Rust 在 Job 收养之后、返回之前写入输入通道。**
  - 优点：“一次”由后端拥有，Rust 真实 PTY 测试能直接覆盖产品逻辑。
  - 缺点：
    - 命令总是先于 CPR 应答，这个顺序缺少现有原生证据；
    - 需要扩展参数校验；`LocalLaunchOptions` 目前派生 `Debug`，需要脱敏；错误不能回显值；
    - 前端仍要做状态反馈。
  - 如果 8.2 证明两种顺序在 Windows 上都安全，B 可以作为以后的简化方案。
- **C（本切片不采用）：把命令放进 argv**（如 `cmd /K`、`-NoExit -Command`、`bash -c '…; exec bash -i'`）。
  - 需要按 Shell 构造引号与参数，会改变第三批的固定 argv 契约。
  - Shell 一启动就可能派生子进程，会落入 ADR 记录的“启动后才加入 Job”窗口。必须先实现“挂起创建 → 加入 Job → 恢复运行”。
  - 它能避开预输入问题，可在 Job 治理完成后另立切片评估。

## 6. 平台差异与已知风险

**macOS**

- 默认 zsh 使用 `-f -i`，但系统 `zshenv` 仍会执行；它的输出或副作用可能出现在命令之前。显式 Bash 按固定候选路径解析（macOS 通常为 `/bin/bash`），参数 `--noprofile --norc -i`。PowerShell 7 若已安装，未验证。
- Shell 切到原始模式前，从机端处于规范模式并开启回显：预输入会先由内核回显一次，Shell 读取后可能再显示一次。
- macOS 规范模式的单行缓冲上限 `MAX_CANON` 为 1024 字节，这是 7 节长度上限的依据；超出部分可能被丢弃。

**Linux**

- 默认 Bash，locale 为 `C.UTF-8`。头文件常量 `MAX_CANON` 为 255，但内核 N_TTY 的实际缓冲（`N_TTY_BUF_SIZE`）为 4096 字节，可以容纳更长的规范模式行。1000 字节上限同样须实测。
- CI 没有安装 Zsh，PowerShell 7 也未实测，都记为未验证。

**Windows cmd**

- 参数 `/D /Q /K`，AutoRun 已禁用。CR 即回车键。
- `%VAR%` 展开、`&` 连接等由 cmd 按自身语法处理：应用不展开，Shell 会解释，这正是命令的本意。
- 非 ASCII 命令的执行效果受代码页影响。第四批只传递 locale 变量，不切换代码页，非 ASCII 相关结果单独记录。

**Windows PowerShell 5.1 / PowerShell 7**

- 参数 `-NoLogo -NoProfile`。`-NoProfile` 不等于禁用历史；PSReadLine 若加载，可能把命令写入磁盘历史文件（未验证）。
- **首次 cmdlet 慢路径**：只引用 [执行记录](RESULTS.zh-CN.md) 的结论，不重新解释根因。在产品白名单环境下，未限定的首次查询有以下观测：

  | 运行 | 测量 | 观测值 |
  | --- | --- | --- |
  | 真实 WebView2 `39759997877` | `(Get-Location).Path` 发送到精确 cwd 行 | 17.8–27.7 秒 |
  | ConPTY framed `40164795306` | 普通首次 q1 | 11.3–27.5 秒（模块限定 22–37 ms） |
  | 准备阶段对照 `40167503032` | 精确发现准备 | 11.8–29.5 秒（显式导入 24–38 ms） |
  | 运行时环境干预 `40166224227` | 替换父 `PSModulePath` 后 | 仍为 11.4–23.0 秒 |

  第四批 Windows 旧 Shell 场景的目录查询停滞（`39063630062`）根因仍未确定。
- 对本切片的影响：
  - 以普通 cmdlet 开头的启动命令，可能在“已提交”后几十秒没有输出。产品不设超时，不重发。
  - 原生验收不能用依赖 cmdlet 的副作用计数来判断“一次”，也不借用或放宽现有 30 秒目录查询门限。

**ConPTY 通用**

- CPR 应答与命令的先后有两种可能（5.1）。“命令先于 CPR 应答”时 conhost 是否行为正常，尚无证据。
- `pty_open` 返回时 Job 已收养 Shell，启动命令派生的子进程会继承 Job。但 Shell 自身初始化期间的派生竞态不变，不能宣称已消除。

## 7. 输入边界与安全

**格式**

- 单行，长度 1–1000 UTF-8 字节，不含追加的 CR。这个上限低于 macOS `MAX_CANON`（1024），也远小于 4096 字节的单块上限。边界值（1000 字节、多字节字符跨边界）须在真实 PTY 实测确认；若实测更小，下调。
- 空字符串表示未配置。只含空白时报错。首尾空格原样保留，不 trim。

**拒绝的字符**

- U+0000–U+001F：包括 Tab、CR、LF、ESC，以及 Ctrl-C/D/Z；在规范模式下，Ctrl-D 会被当作 EOF。
- U+007F 与 U+0080–U+009F。
- 孤立代理项：编码时会被替换为 U+FFFD，发送的内容与所见不同。
- 双向文本覆盖与隔离控制（U+202A–U+202E、U+2066–U+2069）：会让所见顺序与实际顺序不同。如用户需要，可另行放开。

**表单交互**

- 粘贴含换行的文本时必须报错，不能被单行输入框静默删除或替换换行；不同 WebView 对 `<input type="text">` 粘贴换行的处理不同。可沿用环境变量值的 textarea 保留原文再校验，或拦截粘贴事件。
- 输入法组合中按 Enter 不提交表单，列为验证项。

**内容与校验**

- 不做内容黑名单（如 `rm`）。命令等同于用户亲手输入，安全边界是“显式配置、显式提示、只发一次”，不是内容审查。
- 方案 A 只在前端校验：`pty_write` 本来就接受任意用户输入字节，后端不是这里的安全边界。方案 B 以后端为准，前端提前提示。

**隐私**

- 值只存在于会话的内存快照中，不进入以下任何位置：状态文案、toast、窗口标题、`aria-live`、错误信息、console、localStorage/sessionStorage、URL、持久设置。方案 B 下，Rust 错误与 `Debug` 也不回显。
- 值仍会出现在：
  - 终端回显与滚动缓冲；
  - Shell 历史：Bash/Zsh 的 `HISTFILE=/dev/null` 只保留内存历史；PowerShell 见第 6 节；
  - 所执行程序的进程参数。

  因此界面应提示不要填写密码或令牌。本切片不提供凭据管理。
- 原生 trace 工具会以十六进制记录受控测试会话写入的字节，所以测试命令只能使用不敏感的 nonce。这些 trace 是测试工件，不是产品日志。

## 8. 验证方案

### 8.1 浏览器 IPC stub（Playwright）

沿用 `pty-ui-contract.spec.ts`、`local-environment.spec.ts` 的 stub 方式。新增前端 IPC 调用时，同步更新相关 spec 的 stub。断言以 stub 记录的 `pty_write` 为准：

1. **默认不变**：默认一键入口与留空表单的 `pty_open` 参数与 `pty_write` 序列不变。配置了命令时，`pty_open` 参数中不含命令。
2. **CPR 早到**：`ESC[6n` 早于 ID，写入顺序为“CPR 应答、命令+CR”。
3. **CPR 晚到**：`ESC[6n` 晚于 ID，顺序为“命令+CR、CPR 应答”。两种情况命令写入均恰好 1 次，且使用正确的会话 ID。
4. **用户输入**：ID 前的按键、粘贴、`insertText` 不发送；ID 后的输入排在命令之后。
5. **启动失败与关闭**：以下情况都没有命令写入，状态显示“未发送”：
   - open 被拒；
   - open 返回前已 exit；
   - 启动中关闭标签（晚到 ID 被 `pty_close`）；
   - 命令写入前 exit。
6. **写入结果**：
   - 写入被拒（非队列满）→ 显示“未确认”，不重试；
   - 先返回队列满再成功 → 后端只接受一次；
   - `holdWrite` 期间 exit → “未确认”。
7. **重开**：
   - 新 ID 恰好 1 次命令写入，旧会话没有新写入；
   - 连点两次重开只有一个新会话；
   - 启动后修改表单，重开仍用原快照；
   - 清空字段后启动的新会话不发送。
8. **不重发**：resize、切换标签、分屏、聚焦与失焦后都不重发；页面重新加载后不重发。
9. **校验**：控制字符、Tab、CR/LF、粘贴换行、超长（多字节边界）、孤立代理项、双向控制、只含空白，都停留在表单，不产生 IPC；错误文案不回显值。
10. **隐私**：值不出现在状态栏、toast、标题、存储或 URL 中（用恶意文本做字面量测试）。

这些只是浏览器契约，不等于 Rust 或原生成功。

### 8.2 Rust 与真实 PTY：实际副作用计数

方案 A 不改 Rust 产品代码。Rust 侧验证的是传输层与各 Shell 的前提，不是前端的一次性逻辑。

**通用计数方法**

- 每个样本使用新建的临时目录与计数文件。命令向文件追加一行“nonce + 会话标识”；Unix 用 `$$`，PowerShell 用 `$PID`，cmd 只计行数。
- 以 Shell 退出（exit 事件与回收完成）为屏障，再读取文件：退出且回收后，该 Shell 不会再产生副作用；Windows 由 Job 回收后代进程。
- 有界轮询只用于测试等待，产品不依赖。

**Unix**（本机 + CI；`pty_probe` 新阶段或 `#[ignore]` 夹具，`dev-tools` 门控）

- 对每个可用 Shell，在 `open` 返回后立即 `write(命令 + "\r")`。
- 要求：恰好 1 行；同配置重开后再多 1 行，且 PID 不同。
- 边界：1000 字节命令（含多字节 UTF-8）完整到达。
- 对照：只写命令、不加 CR，随后直接关闭会话，计数为 0。用于确认计数来自回车提交的那一行，而不是回显或其他输出。
- 缺失的 Shell 记为跳过，不计为通过。

**Windows**（仅 CI；`pty.rs` `windows_tests` 或独立 `dev-tools` 探针）

- 覆盖 cmd 与 Windows PowerShell，各两个 arm：
  - **R**：先应答 `ESC[6n`，再写命令；
  - **C**：先写命令，再应答。
- 写法：
  - cmd 用 `>>"<绝对路径>" echo <nonce>`，避免 nonce 末尾数字紧邻 `>>` 而被解析为句柄重定向；
  - PowerShell 用 `[IO.File]::AppendAllText` 加绝对路径，尽量不依赖 cmdlet 发现。是否因此避开慢路径须实测，不作结论。
- 要求：每个样本 CPR 应答 1 次，副作用 1 行，正常退出，Job 回收后没有存活进程。
- 期限：另行预注册，不借用或放宽现有 30 秒门限。
- **C arm 失败**说明方案 A 在 CPR 晚到时有风险，需要重新设计并复审；不能用 R arm 通过代替。

**其他**

- 选择方案 B 时，还需 Rust 单测：参数校验、`Debug` 与错误不回显值、只入队一次、入队失败时的会话处理。
- 既有门禁照常执行：all-targets/all-features、fmt、clippy、`tools/wincheck/wincheck.sh`。在方案 A 下，这些全部通过只说明 Rust 未回归。

### 8.3 原生 WebView 验收要点

在 `tests/native/scenarios.mjs` 新增场景 `local-terminal-startup-command`，在 CI 的 Linux WebKitGTK 与 Windows 2022 WebView2 上运行：

1. 新建临时计数文件；在对话框填写命令后启动。
2. 有界轮询，计数变为 1。状态显示“已提交”，DOM 状态、toast 和标题都不含命令。
3. 键入 `exit` 并等待退出，计数仍为 1。
4. 重新打开：计数加 1（Unix 上 PID 不同），旧会话没有新的命令写入。
5. 页面重新加载，或关闭标签后等待既有关闭屏障：计数不变，trace 中没有新的命令写入。
6. 一键默认会话：计数不变。
7. 无效启动目录加命令：启动失败，计数为 0，没有 `pty_write`。

补充要求：

- trace 按写入种类（协议回复、启动命令、用户输入）分类计数，每个会话的启动命令写入为 1 次。
- **Windows**：以 cmd 计数为主；Windows PowerShell 使用 .NET 副作用。从“已提交”到副作用出现的时间只作观察。含 cmdlet 的样本若要做，须另行预注册，结论不外推。
- **macOS WKWebView**：由协调者用 CUA 做单轮（默认 zsh 加显式 Bash）。退出后读取计数文件并截图，记为有限原生验收。
- 现有 7 个场景、首次/重开、中文空格 cwd、30 秒查询与完整 trace 门禁保持不变。

### 8.4 只能记为“未验证”的内容

- macOS WKWebView 自动化：只有 CUA 单轮。
- Linux Zsh；三端 PowerShell 7。
- 非 ASCII 命令在 cmd 代码页下的执行效果。
- 命令中的输入法组合，以及读屏朗读。
- 读取标准输入的交互命令与后续预输入的配合。
- 用户 rc/profile 环境（本项目不加载这些文件）。

- Windows 首次 cmdlet 慢路径与旧 Shell 停滞。

## 9. 需要用户决定的问题

1. **Q1 重开时是否再次发送启动命令？**
   - a.（推荐）再次发送：与 cwd/Shell/env 的“重开继承初始配置”一致，并在重开前明确提示；
   - b. 不发送：重开只恢复其他配置；
   - c. 重开时提供“含启动命令 / 不含启动命令”两个按钮。
2. **Q2 T34 中“命令失败……有明确反馈”是否按“发送状态 + Shell 自身输出与退出码”验收？**
   - a.（推荐）接受：应用级判定成功或失败，需要按 Shell 注入标记或包装命令，不是通用协议；
   - b. 要求应用级判定：本切片暂停，另做方案。
3. **Q3 是否只支持单行，并禁止 Tab 等全部控制字符？**
   - a.（推荐）只支持单行，多条命令用所选 Shell 的连接语法；
   - b. 支持多行，逐行发送：前一行若读取标准输入，后续行会交给该程序；
   - c. 支持多行，作为一次粘贴发送：依赖 Shell 的 bracketed paste，行为不一。
4. **Q4 是否提供“延迟发送”设置？**
   - a.（推荐）本切片不提供：延时不是就绪协议；
   - b. 提供可选秒数，默认 0，并注明“不代表 Shell 已就绪”。
5. **Q5 是否在实施前，用已授权的隔离上游 2.7.0 实测“启动后执行命令”？** 实测内容：发送时机、多行、重开/重连、延迟。需要在用户桌面用 CUA 操作，并备份、恢复共用偏好。
   - a.（推荐）与实施并行，不阻塞：差异记入对照，再由用户决定是否调整；
   - b. 先实测再定 Q1–Q4；
   - c. 不做。
6. **Q6 本切片何时开始实现？** 背景：第四批 Windows 停滞仍未定因，也未获 main 批准。
   - a.（推荐）在 `p1/integration` 上先做前端、浏览器契约和 Unix 真实 PTY；Windows 原生验收与 main 合并请求，等第四批 Windows 结论；
   - b. 等第四批验收完成后再开始。

**用户决定（2026-11-07）**：Q1–Q6 全部采用推荐项，即 Q1a 重开再次发送并在重开前明确提示；Q2a 按“发送状态 + Shell 自身输出与退出码”验收；Q3a 只支持单行，禁止 Tab 等全部控制字符；Q4a 本切片不提供延迟发送；Q5a 上游实测与实施并行、不阻塞；Q6a 先在 `p1/integration` 上实现前端、浏览器契约与 Unix 真实 PTY，Windows 原生验收与 main 合并请求等第四批 Windows 结论。

集成时补充的事实（2026-11-07，第 4 片回归测试实测）：本文第 2 节与第四批计划所写“early FIFO 只接收本地 shell 的 CPR 回复”与当前代码不完全一致。`pty_open` 返回前，凡经 VT 适配器发出的回复都会进入 early FIFO（CPR、DA、XTVERSION、DECRQSS `m` / `"p` / ` q`），xterm 内置回复（DSR 5、DECRQM、OSC 颜色查询、DECRQSS `r`）则被丢弃；用户输入仍不能进入。该边界已由 `tests/e2e/terminal-regressions-*.spec.ts` 固定。实施启动命令时须按实际集合设计排序，不能只按 CPR 推理；是否收紧或放宽该集合另行决定，不在本切片静默修改。
