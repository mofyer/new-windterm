两点需要特别注意，都已由本步测试观测到：

1. **xterm 6.0.0 的 `dispose()` 不清空缓冲区。** 已 dispose 但仍被引用的终端，其全部历史仍占内存（测试 3 的对照组）。所以关闭后能否回收，只取决于是否还有引用残留。
2. **本地终端的输出通道回调要等通道结束才注销。** `@tauri-apps/api` 的 `Channel` 在构造时把回调登记到 Tauri 运行时，收到 `end` 消息后才注销；`main.ts` 不主动注销，而回调闭包引用整个会话。按 Tauri 2.12.3 源码注释，Rust 侧丢弃最后一个通道副本时会发送 `end`。也就是说，前端回收依赖 Rust 端及时释放通道。测试 5 用 stub 复现：关闭标签后、`end` 到达前，终端及其历史仍可达；`end` 到达后才释放。原生 WebView 中 Rust 何时发送 `end`，本步未验证。

## 4. Chrome 观测

### 方法

- Playwright 驱动系统 Chrome 157.0.8103.39（`channel: 'chrome'`，headless），连接 Vite 开发服务器，本机 macOS arm64。
- 每次测量前通过 CDP `HeapProfiler.collectGarbage` 强制两次完整 GC，然后读 `Runtime.getHeapUsage`：`usedSize`（V8 JS 堆）、`backingStorageSize`（ArrayBuffer 后备存储；xterm 每行是一个 `Uint32Array`，主要内存在这里）、`embedderHeapUsedSize`（Blink 堆，波动大，只作参考）。这些计数精确，不需要 `--enable-precise-memory-info`。`performance.memory` 未采用：默认会量化取整，而且不含后备存储。
- 是否释放用两种方式判断：页面内 `WeakRef` 加强制 GC；CDP `Runtime.queryObjects` 按应用实际使用的 xterm `Terminal` 原型统计存活实例（调用前先 GC，用后释放检查器对象组，避免检查器自己持有引用）。
- 单会话测试直接调用生产工厂 `createWorkspaceSession`，`resize` 到固定列宽、24 行，按 4096 B 分块写入 5,224 行，确认缓冲区为 24 + 5,000 行、无软换行。工作台测试用 stub IPC 打开本地终端标签，经 Tauri `Channel` 原样的 index/end 协议送入 4096 B 数据块，等全部 ACK 后再测。

### 结果

下表是最终提交版本 `--repeat-each 10` 的 10 轮范围（每轮新开页面，两个 worker 并行）。开发过程中较早的一轮里，新 worker 的第一项测量曾出现 80 列满行 JS 堆 1.90 MiB、合计 6.48 MiB，属于冷启动波动。

| 负载（5,000 行历史） | 历史增量 | 其中后备存储 | 其中 JS 堆 | 每行 |
| --- | --- | --- | --- | --- |
| 80 列，满行 ASCII | 5.90 MiB | 4.58 MiB | 1.32 MiB | 约 1.24 KB |
| 80 列，短行（`line 000123`） | 5.60–5.71 MiB | 4.58 MiB | 1.02–1.13 MiB | 约 1.17–1.20 KB |
| 80 列，混合（真彩色、CJK、emoji 组合序列、组合附加符） | 7.05–7.07 MiB | 4.58 MiB | 2.47–2.49 MiB | 约 1.48 KB |
| 200 列，满行 ASCII | 12.55–12.56 MiB | 11.45 MiB | 1.10–1.11 MiB | 约 2.63 KB |

- 后备存储等于 `历史行数 × 列数 × 12 B`（xterm 6.0.0 每格 3 个 `Uint32`），与行内容长短无关：短行和满行一样大。JS 堆部分纯文本约每行 210–280 B，混合内容约 520 B。估算公式：**每会话热历史 ≈ 行数 × (列数 × 12 + 约 250) B**，内容含大量组合字符时再加约 270 B/行。
- 空终端（24 行可见、未写入）固定开销约 0.25–0.30 MiB；Blink 堆增量在 −0.6 至 +0.7 MiB 之间波动，不计入结论。
- 已 dispose 但仍被引用：内存不降（80 列满行仍有约 6.08 MiB）。去掉引用后，强制 GC 即回到基线（剩余 0.04–0.32 MiB），`WeakRef` 已清空。
- 工作台本地标签（视口 1280×800，经 fit 后为 114 列 × 20 行，5,020 行缓冲）：退出后历史与行内容不变，终端实例数仍为 2；关闭后实例数回到 1，释放 7.66–7.67 MiB（后备存储 6.62 MiB）。关闭时若通道未结束，释放量约为 0（−0.04 MiB）；补发 `end` 后释放 7.71 MiB。

推算（按上式，未实测）：8 个标签都在 80/200 列写满时约 50/100 MiB；1000 列 × 500 行的极端尺寸下单会话约 64 MiB。若把热历史直接设为上游默认 999,999 行，80 列单会话约 1.1 GiB，这条路不可行。P0 压缩历史概念验证的负载原始约 36 B/行，压缩后约 4.9 B/行；同样负载下 999,999 行冷归档约 5 MB，但实际比例取决于输出内容。

### 局限

- 以上都是 **Chrome/V8 的观测**，不是 WKWebView（JavaScriptCore）、WebView2 或 WebKitGTK 的结论；也不是渲染进程或应用进程的 RSS，不含 GPU、分配器碎片和 Rust 侧内存。
- 强制 GC 只是测量手段。生产环境不会主动 GC，峰值内存高于这里的稳态，关闭后的内存要等下一次 GC 才归还。
- `WeakRef`/`queryObjects` 只说明这个页面里还有没有强引用。stub 按 Tauri `Channel` 协议模拟 `end`，但 Tauri 运行时的真实回调表、Rust 何时丢弃通道、原生 IPC 序列化都没有测到。
- 负载是合成的固定行；长逻辑行软换行、频繁属性变化、超链接、SIXEL 图片的扩展属性都会改变每行开销。12 B/格依赖 xterm 6.0.0 的内部格式，升级时需要重测（终端内核 ADR 的 G-UPGRADE 门禁）。
- 只在一台本机上运行，没有进 CI；数值供量级判断，不作为性能门限。测试断言只守护常量、裁剪、“小于 64 MiB”的量级、后备存储与理论值同量级（0.5–2 倍）以及释放/保留，不把具体字节数当通过条件。

## 5. 预算定义（建议，待用户决定）

**术语。** 热历史：xterm 缓冲区里的回滚行，属于活动终端状态，可直接滚动、选择。冷历史：已离开热窗口、按逻辑行压缩保存的只读记录（Q04），不是终端状态。

1. **单会话热历史**：固定行数 `DEFAULT_SCROLLBACK_LINES`，保持 5,000 行。它同时是冷归档的捕获窗口，必须大于单次写入可能新增的行数（4096 B 数据块最坏约 4,096 行），因此不能低于 5,000。热历史内存随列数线性增长，上限按 1000 列估算。
2. **单会话总历史（Q06）**：行数上限与上游默认一致，按 999,999 行设计，超出热窗口的部分进入冷归档。“0”或“无限”的语义等上游实测后再定，不先猜测。
3. **单会话冷归档字节预算**：按压缩后字节计，建议初值 64 MiB（以 P0 负载推算，约可容纳千万行），实际数值等原生测量后确定。
4. **全局预算**：每窗口 8 个标签（包括已退出的标签）；热历史最坏 8 × 单会话。冷归档全局建议初值 256 MiB，超过时从最久未使用的已退出标签开始裁剪。多窗口目前未开放，开放时按应用汇总。
5. **超出时的行为**：
   - 热窗口满：最旧的行转入冷归档，不丢数据。第 5 步起原生会话已捕获冷归档（第 11 节），但还没有浏览界面、预算执行和提示；超过 5,000 行的历史只存在于归档中，用户暂时看不到，Q06 仍未对齐。
   - 冷归档超出单会话或全局预算：按整块删除最旧的压缩块，记录丢弃的行数，并在状态栏和该会话的历史视图顶部显示“已丢弃最早 N 行”；不静默丢弃。
   - 捕获时发现缺口（行在归档前已被裁掉）：计数并提示，不伪造连续性。
   - 备用屏幕（vim、less 等）不进入任何历史。

## 6. 关闭与退出后的回收要求

| 事件 | 要求 | 本步验证 |
| --- | --- | --- |
| 进程退出 | 标签、热历史、冷归档全部保留，可读、可搜索、可复制；不再接收输入；仍计入标签上限与全局预算 | Chrome：退出后历史逐行不变、实例仍在 |
| 重新打开 | 新建标签和新 xterm，不复制旧历史；旧标签保持原状 | 既有生命周期契约测试 |
| 关闭标签 | 后端关闭成功后释放 xterm、VT 适配器、元素、输入队列、冷归档和只读视图；之后不得有任何强引用，包括输出通道回调；关闭失败时保留标签供重试（现有行为） | Chrome：退出后关闭即释放；运行中关闭在 R1 实现后也即释放，不等通道 `end`；第 5 步起冷归档同样在关闭后释放（第 11 节） |
| 页面重载/窗口销毁 | 前端逐个 dispose；Rust 按窗口代际关闭会话；冷归档只在内存中，随页面丢弃 | 既有测试；本步未新增 |
| 应用退出 | Rust `shutdown()`；不把历史写入磁盘，除非用户另行决定 S07 | 未测 |

要求 R1：关闭标签后，回收不能依赖 Rust 端发出 `end` 的时机。前端应在关闭时让通道回调不再引用会话。**已实现（2026-11-07，协调者集成）**：会话生命周期已拆到 `session-lifecycle.ts`，`Session` 保存自己的输出 `Channel`，后端关闭成功后把它的 `onmessage` 换成空函数并清除引用；没有选择立即注销回调，因为后端之后仍可能发送 `end`，注销会产生找不到回调的警告。测试 5 已改为“关闭运行中标签即释放、不等通道 `end`”：Chrome 本机观测关闭时释放 7.66 MiB、`end` 后再释放 0；临时移除这一行后该测试失败（实例数 2），恢复后通过。以上是 Chrome 与 IPC stub 观测，Rust 何时真正丢弃通道仍未测。

要求 R2：任何新增的会话级资源（冷归档、搜索索引、只读视图）都要挂在会话的关闭路径上，并在测试里用同样的 `queryObjects`/`WeakRef` 方法验证。

## 7. 标签与分屏状态的不变量

1. 每个会话恰好拥有一个活动 xterm。这个 xterm 是该会话屏幕与热历史的唯一来源；同一字节流不能再交给第二个解析器。
2. 一个窗格同时只显示一个会话，一个会话的元素同时只在一个窗格中。若上游允许同一会话出现在两个窗格（镜像），第二个窗格只能是只读投影，须先实测上游再决定。
3. 切换标签、隐藏、分屏、取消分屏都不截断历史，也不释放内存；隐藏的会话继续解析输出。只有关闭才释放。
4. 分屏只改变显示哪些已有会话；现有“会话不足 2 个时先建一个演示会话”的行为保持，并计入标签上限。
5. 关闭分屏中的会话后，活动标签按现有规则落到第一个剩余标签。上游默认 `SelectPreviousTab` 与此不同，留给 G46 实测后处理，本片不改。
6. 改变尺寸时 xterm 重排热历史；冷归档按逻辑行保存，与列宽无关，回放时按当前列宽换行。
7. 标签上限对所有类型和已退出标签一视同仁；预算按标签计算，不按进程计算。

## 8. 压缩历史接入方式（不成为第二份活动终端状态）

冷归档是从 xterm 派生出的只读、只追加的记录，不是第二个终端。具体约束：

1. **单一来源**：只在 xterm 写入回调之后，通过公开 API 从 xterm 缓冲区读取已经离开屏幕的逻辑行。不直接接收 PTY/SSH 字节流，不自己解析 VT 序列。
2. **不带终端状态**：只存文本和 SGR 属性，不保存光标、模式、字符集、滚动区或备用屏幕，也没有输入路径。终端复位、模式切换只影响 xterm。
3. **只读投影**：越过热窗口的浏览、搜索（G20）、折叠和大纲（G16/G17）由只读视图从归档回放，视图有自己的 xterm 实例但 `disableStdin`、不连后端，按需创建、只渲染视口附近（虚拟化），用完即释放，内存计入该会话预算。回到底部时回到活动 xterm。
4. **一致性规则**：热窗口与冷归档交界用 xterm marker 跟踪（P0 已验证），被裁掉即记缺口；“清回滚”（T32）与 RIS 是否连带清冷归档，按上游实测决定后统一实现。
5. **边界**：接入点放在终端内核 ADR 的 H4 边界（逻辑行读取、marker、写入回调），xterm 是第一个实现。冷归档先放在 WebView 内；只有原生测量显示内存不可接受时，才按 ADR 门禁评估移入 Rust。移入 Rust 也只能存冷块，不能在 Rust 再维护屏幕。

## 11. 第 5 步实施记录（2026-11-07）

分支 `p1/history-archive-capture`，基于 `p1/integration` 的 `a98c280`。只改前端，不改 Rust、IPC、用户可见文案或 DOM；没有新增依赖。

### 接入点与数据流

- **H4 边界**：新增 [`terminal-core.ts`](../../apps/desktop/src/terminal-core.ts)，目前只含历史所需能力：`HistorySource.read()` 返回自上次读取后完全离开屏幕的逻辑行（自动换行的多行合并，文本加 SGR）以及是否出现缺口、是否被清除。xterm.js 是唯一实现，只用公开 API（`buffer.normal`、`getLine`/`isWrapped`/`getCell`/`translateToString`、`registerMarker`）。它不接收字节流、不解析 VT、不保存光标/模式/字符集/屏幕状态，也没有写入或输入路径；唯一的解析器用法是两个返回 `false` 的观察者（`ESC c` 与 `CSI 3 J`/`CSI ? 3 J`），只记下“发生过复位或清除滚动历史”，xterm.js 与 VT 适配器照常执行自己的处理。读取发生在写入回调里，不在观察者里。
- **归档**：[`history-archive.ts`](../../apps/desktop/src/terminal-compat/history-archive.ts) 改为只依赖 `HistorySource`，不再直接读 xterm；每 512 行（`ARCHIVE_BLOCK_LINES`）以 `deflate-raw` 压缩为一块。压缩失败时该块原样保留并计数，不丢历史。`dispose` 注销观察者与 marker，立即丢弃全部块和待压缩行；之后完成的压缩结果也被丢弃。
- **会话**：[`history-capture.ts`](../../apps/desktop/src/history-capture.ts) 为每个原生会话（本地、SSH、Telnet/Raw TCP）创建一个归档，在 `session-lifecycle.ts` 的 `terminalChannel` 里与输出通道一起创建。数据流：Channel `data` → `Utf8Boundary` → `xterm.write(块, 回调)` → 回调中先做原有的 `s.disposed` 检查、诊断计时和 `acknowledge`，**然后**调用 `capture()`，再 `host.progress`。ACK 仍在 xterm 解析该块后按序入队，入队顺序、64 KiB/64 块预算、背压和 15 秒超时都没有改；捕获在下一块解析前同步完成，异常被拦在内部（停止该会话的归档并计入诊断），不会进入 xterm 写入循环或 ACK 链。演示会话没有归档。
- **关闭（R2）**：`close()` 在后端关闭成功、断开通道回调之后调用 `history.dispose()` 并清除引用；`shutdown()` 同样释放。进程退出不释放，已退出标签保留归档直到关闭（决定 5A）。没有改动打开、输入、尺寸和重开路径。
- **预算**：`history-budget.ts` 新增 `HISTORY_TARGET_LINES = 999_999`、`ARCHIVE_BLOCK_LINES = 512`、`MAX_SESSION_ARCHIVE_BYTES = 64 MiB`、`MAX_TOTAL_ARCHIVE_BYTES = 256 MiB`，均注明为暂定值。本步**只统计、不裁剪、不提示**：超预算只在开发诊断里计数。

### 恢复位置与缺口语义

本步在 Chrome 中先用 P0 原型复现了两个会在生产中出现的问题（临时实验，未提交）：Ctrl-L（`ESC[H ESC[2J`）会清掉放在屏幕首行的 P0 前沿 marker，原型随即记 1 次缺口并从第 0 行重新归档，40 列 × 5 行、100 行历史的实验里 16 行各出现两次；RIS 替换了缓冲区但旧 marker 不失效，实验中复位后 80 行只归档了 30 行。另据 xterm.js 6.0.0 源码，加宽重排会删除续行并销毁其上的 marker，在屏幕顶部插入行（IL）会把 P0 前沿 marker 下移。现行做法：

1. marker 放在**最后一个已归档逻辑行的首行**。它在滚动历史里，屏幕上的擦除、删除行不会触及它；加宽重排不会删除逻辑行首行。下次从该逻辑行结束后的一行继续。尚未归档任何行时，marker 放在要开始读取的那一行。
2. marker 因裁剪而丢失（缓冲区已满）时记 1 次缺口，从第 0 行继续；在读到新行之前继续丢失只算同一个缺口（例如一个长于热窗口的逻辑行持续丢失开头）。缺口之后的第一行可能是不完整的逻辑行。
3. RIS 与 ED 3（`clear` 会发送）计为“清除”，不计缺口，从第 0 行继续；此前已归档的行保留。同一块里在复位或清除之前滚出屏幕的行不会归档。“清回滚”是否连带清空冷归档仍按 T32 留待上游实测。
4. 屏幕变高把已归档行拉回屏幕、随后又被擦除时，无法知道继续位置：从当前屏幕顶部继续并记 1 次缺口，不重复归档，可能少记几行。这是已知的剩余情况，浏览器测试覆盖。
5. 程序化调用 `terminal.reset()`/`clear()` 不经解析器，无法观察；生产代码只在没有归档的演示会话上调用 `clear()`。

逐行编码也有改动：每一行都去掉最后一个已写字符之后从未写入（或已擦除）的单元格，宽字符换行时留下的填充格不再变成空格；程序实际写出的行尾空格保留。带背景色的擦除只在延伸到逻辑行最后一行的末列时保留（P0 保留任意末尾有色单元格），ECH 等未到行尾的有色空白会丢失颜色。逐格读取只到内容结束处，默认属性的单元格不再逐格生成 SGR。

### 开发诊断

`?p0Diagnostics`（仅开发构建）的快照新增 12 个数字：`historyArchives`、`historyArchivedLines`、`historyGaps`、`historyClears`、`historyCompressedBytes`（存活归档合计）、`historyMaxSessionCompressedBytes`（本页面生命周期内单会话峰值，关闭会话后不回落）、`historySessionBudgetExceeded`、`historyTotalBudgetExceeded`、`historyUncompressedBlocks`、`historyCaptureErrors`、`historyCaptureMs`、`historyMaxCaptureMs`。只记录数字，不记录历史文本、路径或会话 ID；预算计数基于异步压缩完成后的字节数，会滞后一个捕获周期。捕获异常时该会话停止归档并释放，其后的统计不再计入。按 [WEB_QA](../p0/WEB_QA.zh-CN.md) 的做法，`npm run build` 后在 `dist` 的 JS 中搜索诊断对象名、查询参数和全部 25 个字段名（原有 13 个加新增 12 个），27 个标记都没有出现；冷归档本身（`deflate-raw`、`registerMarker`）在生产构建中。
