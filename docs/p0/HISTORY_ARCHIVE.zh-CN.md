# 压缩滚动历史概念验证（Q04 / Q06）

日期：2026-10-11。依赖：`@xterm/xterm 6.0.0`。状态：**隔离实验通过，未接生产终端；不代表 Q04/Q06 验收或 WindTerm 行为对照完成。**

## 要回答的问题

FEASIBILITY 把“大规模历史 + 动态压缩”列为 xterm.js 路线的阻断风险：增大 `scrollback` 只是保留更多未压缩的行；若在 Rust 侧另存一份历史又会与 xterm 内存重复。P0 需要证明是否能用 **有界热窗口 + 压缩冷历史** 保持内容、检索与行号一致，且不静默丢数据。

## 结论

**可行，且只依赖 xterm 公开 API。** [`history-archive.ts`](../../apps/desktop/src/terminal-compat/history-archive.ts) 证明：

- xterm 只保留有界热滚动历史（实验中 1,000 行）；每个完全滚出屏幕的**逻辑行**（自动换行的多行合并）连同 SGR 属性写入冷归档，每 512 行以浏览器原生 `deflate-raw` 压缩为一块。
- 归档前沿用 xterm marker 标记：xterm 在重排（resize）和裁剪时会移动 marker，行被裁掉时 marker 失效。失效即记为**数据缺口**并上报，不会悄悄丢行。
- 归档行可按绝对行号读回，能回放到新的 xterm 中还原文本、宽字符与颜色；搜索逐块解压，覆盖冷块与尚未封装的末块。
- 备用屏幕（vim、less 等）不会进入历史，与终端语义一致。

## 实测（headless Chrome，macOS arm64，本机）

| 场景 | 结果 |
| --- | --- |
| 5 万行（含中文与 emoji），按 4 KiB 分块写入，分块切断行与 UTF-8 | 归档 49,977 行（其余仍在屏幕上），逐行比对 0 处不一致，0 缺口；xterm 缓冲恒为 1,024 行 |
| 体积 | 原始 1,793,674 B → 压缩 243,467 B（约 7.4 倍）；压缩总耗时 62 ms |
| 写入开销 | 开启归档 2.51–2.55 s，对照组 2.32–2.40 s，约 +5%（顺序固定、未随机化，仅作量级参考） |
| 2 万行、78 个压缩块搜索 | 冷块命中与末块命中的绝对行号、列号准确，不存在的词返回空；三次搜索共 35 ms |
| 重排 | 20 → 13 → 31 列两次 resize，90 条换行的长逻辑行全部完整归档 |
| 属性回放 | 粗体、16/256/RGB 前景、RGB 背景、宽字符逐格还原 |
| 热窗口过小 | 单次写入行数超过热窗口时报告 1 次缺口 |

## 约束与未完成

- **每次写入新增的行数必须小于热窗口**，否则归档前就被裁掉（会被检测为缺口）。当前 PTY/SSH 每块 ≤ 4,096 字节，最坏约 4,096 行，生产接入时热窗口需 ≥ 5,000 行，或在 Rust 侧拆分写入。
- 冷历史目前只能读回和搜索，**还没有浏览界面**：用户向上滚动越过热窗口时，需要一个由归档回放的只读视图。这也是折叠（G16）可以依托的位置，需单独验证。
- 只保存文本与 SGR 属性：OSC 8 超链接、图片、行级时间戳尚未保存；时间戳（G 系列）需要在捕获时附加。
- 压缩在 WebView 中执行。若要让内存上限独立于 WebView，可改为把逻辑行送到 Rust 存储，接口不变。
- 内存数字是归档的 JS 字节数，不是进程 RSS；尚未在原生 WKWebView 中测量，也未与 WindTerm 2.7.0 的实际压缩行为和容量对照。
