# 端口转发与跳板概念验证（C08、C10、C16、C17、C18）

日期：2026-10-11，2026-10-12 补充 SSH 终端的端口转发与 agent 转发界面。状态：**Rust 协议层探针通过；已打开的交互 SSH 终端可经 IPC 与「端口转发」面板添加本地、动态、远端转发，但只对本仓库的 russh 夹具和浏览器 IPC stub 验证过，没有配置保存，不代表这些功能验收。** 对端为本仓库的 russh 有限命令服务端（已加入只连回环地址的 `direct-tcpip` 支持），不是 OpenSSH。

## 结论

[`ssh_forward.rs`](../../apps/desktop/src-tauri/src/ssh_forward.rs) 证明在现有 russh 0.64.1 会话上可以实现三项能力：

- **本地转发（`ssh -L`，C16）**：只在回环地址监听，每个本地连接对应一个新的 `direct-tcpip` 通道；双向搬运时正确处理半关闭（本地 EOF 发送通道 EOF，通道 EOF 关闭本地写端），两个方向都结束后关闭通道。最多 64 个并发连接，停止时关闭监听和全部连接。
- **动态转发（`ssh -D`，C18）**：最小 SOCKS5（RFC 1928）实现，无认证、仅 CONNECT，支持 IPv4、IPv6 与域名地址；其它命令先读完整个请求再回复“命令不支持”。
- **跳板（`ssh -J`，C08）**：经第一跳的 `direct-tcpip` 通道读取第二跳的主机密钥供用户确认，再在同一通道上建立第二个 SSH 会话，固定校验第二跳自己的密钥并独立认证。每一跳都有独立的主机信任。

## 实测（`cargo test --lib forward`，连续 3 轮）

| 场景 | 结果 |
| --- | --- |
| 本地转发 4 路并发，每路 256 KiB 往返 | 逐字节一致，服务端记录 4 个 `direct-tcpip` 通道 |
| 重复绑定同一端口 / 绑定 `0.0.0.0` | 前者返回“地址已占用”，后者被拒绝（只允许回环） |
| 目的地不可达 | 只关闭该客户端连接，监听继续服务 |
| 停止转发 | 监听关闭，新连接被拒绝 |
| SOCKS5 按 IPv4 与按域名 CONNECT | 握手成功，256 KiB 往返一致；BIND 返回 0x07 |
| 跳板 | 经第一跳读到的第二跳密钥与真实密钥一致；第二跳 shell 中 `exit` 得到退出码 7；第二跳固定错误密钥时在认证前失败，服务端认证次数不变 |

## 排查记录

初次运行时转发数据往返失败。排查发现原因在测试夹具：russh 服务端会把**所有通道**的数据都交给 `Handler::data`，而夹具的行式 shell 把转发字节当作命令处理，单行超过 256 字节时断开整个会话。修复后夹具只处理交互 shell 所在通道的数据，原有 SSH 集成测试仍为 13/13。转发代码使用与终端相同的 `wait`/`data` 读写两半，并显式处理 EOF 与关闭。

## 远端转发与 agent 转发（C17、C10）

服务端主动打开的通道过去会被 russh 客户端的默认实现**全部接受**（session、direct-tcpip、forwarded-tcpip、agent、X11）。现在 `KeyCheck` 持有每条连接的路由表，只接受登记过的通道：

- **远端转发（`ssh -R`）**：`remote()` 向服务端申请监听并登记“远端地址:端口 → 本地目标”；只有登记过的 `forwarded-tcpip` 通道会被接受并连到本地目标（5 秒连接期限），其余一律拒绝。固定端口先登记再申请，服务端选择的端口在应答后登记；`cancel_remote()` 移除路由并取消监听。
- **agent 转发**：只有该连接显式开启后，才接受服务端的 agent 通道并连到本机 agent（Unix `SSH_AUTH_SOCK`，Windows OpenSSH agent 命名管道）；默认拒绝。
- **X11 转发**（2026-10-12 加入，C15）：只有该连接显式开启后才接受 `x11` 通道，先校验假 cookie 再连本机 X 服务，随终端结束；默认拒绝。见 [X11 决策记录](X11_GSSAPI_ADR.zh-CN.md#已实现探针2026-10-12)。

其余服务端主动打开的通道一律拒绝。实测（russh 夹具）：远端转发 2 路往返一致；移除路由后服务端打开的通道被拒绝、服务端连接无数据关闭；取消后服务端不再监听；绑定 `0.0.0.0` 被拒绝。agent 转发未开启时服务端得到 `AGENT REFUSED`；开启后经转发通道查到临时 agent 中的 1 把公钥。

## SSH 终端的端口转发：IPC 与界面（C16、C17、C18）

### 设计

- **共用终端连接**：`ssh_open` 的连接改由 `connect_routed_with`（`connect_routed` 加上终端自己的传输参数、键盘交互提示与 rekey 标志）建立，并持有这条连接自己的 `Routes`，因此可以登记远端转发。转发与 shell 共用这一条已认证、已固定主机密钥的连接，不会另建连接或再次认证。转发由 [`ssh_tunnels.rs`](../../apps/desktop/src-tauri/src/ssh_tunnels.rs)（挂在 `ssh::terminal::tunnels`）管理，归属于终端会话。
- **命令**：`ssh_forward_add`（参数 `id` 为终端会话 ID，`forward` 为 `{kind, bindHost, bindPort, targetHost, targetPort}`，`kind` 为 `local` / `dynamic` / `remote`）返回 `ForwardInfo`，其中是**实际**绑定的地址和端口（端口填 0 时由系统或服务器选择）；`ssh_forward_remove`（`id`、`forwardId`）；`ssh_forward_list`（`id`）。三个命令都已登记在 `generate_handler!`、`build.rs` 和 `capabilities/main.json`，每次调用都按窗口校验终端归属。
- **输入校验**：本地与动态转发只监听回环 IP 字面量（`127.0.0.0/8`、`::1`；`localhost`、`0.0.0.0`、`::`、IPv4 映射地址都拒绝）；远端监听地址和目标主机须为主机名（以点分隔的标签，每段 1–63 个字母、数字、`-`、`_`，不以 `-` 开头，总长不超过 253）或 IP 字面量（含 `:` 时须能解析为 IPv6 地址，不加方括号）；目标端口 1–65535，监听端口 0–65535；动态转发不能带目标，本地与远端转发必须带完整目标；IPC 结构拒绝未知字段。每个终端最多 16 个转发；每个本地监听最多 64 个并发连接；远端转发的服务端通道每条连接共享 64 个上限。已登记的固定远端地址和端口再次申请时，在发给服务器之前就被拒绝，避免覆盖原有路由。前端在调用前做同样的检查（IPv6 回环的各种写法如 `0:0:0:0:0:0:0:1` 都按 `::1` 接受）。
- **生命周期**：终端因任何原因结束（shell 退出、关闭标签 `ssh_close`、页面重新加载或关闭窗口 `close_owner`、退出应用 `shutdown`）时，在报告退出事件**之前**只做本地工作：清空远端路由（服务器之后打开的通道立即被拒），结束远端转发和 agent 的全部转发连接（包括两端都空闲的连接），停止所有本地监听并关闭其连接。报告退出之后，再在 3 秒内请求服务器取消远端监听；在此之前 SSH 连接保持打开，所以网络应答不会推迟退出事件。正在进行的添加遇到关闭时会撤回已取得的监听或远端端口。移除远端转发时先删路由再请求取消；服务器 3 秒内未确认时界面提示“本地已移除，服务器未确认停止监听”，并重新列出转发。
- **转发连接的结束**：服务器对某个转发通道发 EOF 后，本地数据仍可继续上行，直到本地结束或服务器关闭通道；服务器关闭通道或整条连接结束时，转发连接立即结束，不再等待空闲的本地一端。
- **状态与连接数**：本地和动态转发显示“监听中”或“已停止”（监听任务自行结束时）以及实时连接数（含 SOCKS5 握手中的连接）；远端转发只显示“服务器监听中”，不按单个转发计数。

### 共用连接的流量控制

russh 0.64.1 客户端在**收到**数据时就扩大服务器的发送窗口，然后等待该通道的有界队列（终端连接为 16 条消息）有空位。某个转发的本地客户端停止读取时，原来的转发实现会停止读取通道，进而卡住整条连接：终端和其它转发都不再有数据。新增的测试复现了这一点（修复前，另一个转发 5 秒内无法完成往返）。

现在每个转发连接（本地、动态、远端、agent）都通过 [`ssh_forward_flow.rs`](../../apps/desktop/src-tauri/src/ssh_forward_flow.rs) 持续读取通道：本地客户端落后时最多先缓存 64 KiB 服务器数据；超过后只等待本地写入，若 5 秒内没能把积压降回 64 KiB 以内，就断开这一个转发连接（关闭通道和本地套接字），整条连接随即恢复。服务器结束通道后，这个转发不再拖住整条连接，5 秒上限改为按每次写入计算：持续在读的慢客户端能收到剩余数据，完全不读的客户端 5 秒后被断开。代价与边界：

- 读得慢但一直在读的客户端不会被断开（测试：每 5 ms 读 16 KiB，2 MiB 全部收到），但缓存满时整条连接会随它短暂等待，与修改前相同；
- 完全停止读取的客户端会让终端最多停顿约 5 秒，然后该连接被断开；多个这样的客户端各自造成一次停顿，没有按会话限制停顿中的连接数；
- 跳板管道（`pipe()`）不设停顿上限，仍像以前一样等待第二跳的 SSH 会话读取：外层连接上只有这一个通道，等待不会拖住别的通道；
- 这与 OpenSSH 按通道窗口的流控不同：OpenSSH 只会暂停这一个通道，不会断开它。

另外，远端转发的连接到达时，`KeyCheck` 过去在连接事件循环里同步连接本地目标（最长 5 秒），本地目标不可达时会让共用连接上的终端停顿；现在改为在独立任务中连接，成功后才接受通道，失败则拒绝。

### 界面

已连接的 SSH 标签在终端工具栏显示「端口转发」按钮（连接前、断开后禁用；其它标签隐藏），命令面板也有「SSH 端口转发 · 当前 SSH 标签 · 仅桌面」。面板（[`port-forward.ts`](../../apps/desktop/src/port-forward.ts)）列出每个转发的类型、监听地址、目标、状态和连接数，可添加、移除和刷新；打开期间每秒刷新一次，并丢弃过期的列表应答。所有来自用户和后端的值都以文本渲染。配置不保存。终端结束后面板显示“会话已结束”并禁用表单。

## SSH 终端的 agent 转发：IPC 与界面（C10）

2026-10-12 加入。**只对本仓库的 russh 夹具、私有临时 `ssh-agent` 和浏览器 IPC stub 验证过，没有对 OpenSSH 服务端实测，不代表 C10 验收。**

### agent 转发的设计

- **逐连接显式开启**：连接 SSH 终端的对话框里有复选框“转发本机 ssh-agent（仅对信任的主机）”，只在终端用途中出现（验证与文件浏览不显示），默认不勾选，关闭对话框即清除，不写入任何存储。勾选后立即显示警告：连接期间远端主机（以及能控制它的任何人）可以让本机 agent 用其中的全部密钥代你签名，私钥本身不离开本机；核对指纹时再次提醒（跳板主机那一步不提醒，转发只发生在目标主机的连接上）。
- **IPC**：`ssh_open` 增加可选参数 `agentForwarding`（缺省为关闭），前端只在勾选时发送 `true`。没有新增命令。探针 `ssh_probe` 不携带这个选择。
- **Rust**：`Ssh::open_with_agent`（[`ssh_agent_forward.rs`](../../apps/desktop/src-tauri/src/ssh_agent_forward.rs)，挂在 `ssh::terminal::agent`）在开启时：
  1. 只读取一次本机 agent 的位置（Unix `$SSH_AUTH_SOCK`；Windows 为 OpenSSH agent 命名管道，与 agent 认证共用 `AGENT_PIPE` 常量），并在不连网络、不消费 challenge 的情况下确认它现在能连上（Unix 2 秒期限）；连不上时直接失败，不认证；
  2. 连接、认证并申请 PTY 后，先把这个位置登记到这条连接自己的 `Routes`（`Routes` 现在保存 agent 的路径，而不是一个开关；中继不再读取进程环境变量），再在终端的 session 通道上发送 `auth-agent-req@openssh.com`（要求应答）；
  3. 服务器拒绝时清除这条路由，整个打开失败（`SSH server refused agent forwarding`），而不是静默地不转发；与 X11 的逐连接开启一致；
  4. 之后服务器打开的 `auth-agent@openssh.com` 通道由已有的 `KeyCheck` 路由接受并中继到登记的位置；其他连接（包括同一窗口的其他终端、SFTP 授权的每次重连、跳板主机那一跳）没有登记，始终拒绝。
- **生命周期**：终端结束时 `Tunnels::close` 调用 `Routes::end_relays`，关闭 agent 路由并结束已建立的 agent 中继，与端口转发、X11 相同。
- 打开成功后，终端状态栏显示“SSH 已连接 · 已转发本机 ssh-agent”。

## 经代理连接与 ProxyCommand（C07、C19、C20）

[`ssh_proxy.rs`](../../apps/desktop/src-tauri/src/ssh_proxy.rs) 把三种连接方式都变成一条字节流，再交给与直连相同的“固定主机密钥 + 认证”流程：

- **HTTP CONNECT 代理**：可选 Basic 认证；逐字节读取响应头（≤ 8 KiB），不会吞掉隧道里的数据；非 200 响应原样报告状态行。
- **SOCKS5 代理**：无认证或用户名/密码（RFC 1929）；IPv4、IPv6、域名目标；失败时报告代理返回的错误码。
- **ProxyCommand**：**不经过 shell**，自行按空白与引号拆分参数（单引号原样、双引号支持 `\"` 与 `\\`），只替换 `%h`、`%p`、`%r`、`%%`，其它 `%` 序列直接拒绝；`;` 等 shell 语法只是普通参数。子进程的 stdin/stdout 经阻塞线程桥接为异步流，进程对象释放时结束并回收子进程。没有为此启用 tokio 的 `process` 特性，避免引入新依赖。

实测（`cargo test --lib proxy`）：经 HTTP 代理读到的主机密钥与真实密钥一致，并能完成认证、在 shell 中 exit 7；带认证的 HTTP 代理在缺少凭据时返回 407，提供凭据后成功；SOCKS5 有/无登录都成功，密码错误被拒；`/usr/bin/nc %h %p` 作为 ProxyCommand 完成会话，释放后子进程不再存在，不存在的命令报错。ProxyCommand 测试只在有 `/usr/bin/nc` 的 Unix 上运行。
