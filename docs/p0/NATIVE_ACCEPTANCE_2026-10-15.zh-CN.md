# 2026-10-15 macOS 原生验收观察

本轮取得了真实 WKWebView / 本地 PTY 的单次系统拼音提交、有限输出中断、大段粘贴字节完整性和粘贴控制字符过滤证据。自动化观察中出现 **AX 文本继续更新、CUA 截图中的终端画面停留在旧内容** 的现象；随后用户将应用置前台，确认两条 marker 正常显示，CUA 截图与 AX 回读也与用户结果一致。前后台/可见性差异仍待定位，**不据此认定前台终端缺陷**。另有旗帜字形和 shell 编辑行残留问题。本报告不表示原生显示全场景、完整 IME、性能预算或 P0 出口通过。

4. 操作结束后移除临时拼音输入源；系统设置中的输入源列表恢复为 **ABC + 豆包**。这只证明列表恢复，**没有证明当时实际激活的输入源**。

## 3. 粘贴：真实 PTY 接收字节校验

本轮在真实本地终端内使用有界 raw 接收器接收已知测试载荷，并以字节数与 SHA-256 核对结果。它证明指定载荷在该轮输入路径的结果，不证明任意 shell、SSH、Telnet 的粘贴行为。

### 3.1 1 MiB 中文与 ASCII 混合载荷

- 载荷：`'中A'.repeat(262144)`；UTF-8 中每组为 4 字节，共 **1,048,576 B**。
- 接收器结果：`bytes=1048576`，`match=True`。
- SHA-256：`fb0a26286f47eea0651b91a98930e362d56e552c85cd915da4ec8c24548e8b76`。

这次结果支持该载荷经真实 WKWebView → 输入队列 → Rust → PTY 完整送达。没有测得粘贴完成耗时、输入排队延迟预算或粘贴期间取消行为。raw 接收器也不等于 shell 多行命令编辑、执行或 bracketed paste 的完整验收。

### 3.2 ESC 控制字符过滤

- 输入测试文本：`P0_BEGIN\x1b[201~P0_END`，其中 `\x1b` 表示一个实际 ESC 控制字符。
- 预期过滤结果：`P0_BEGIN[201~P0_END`，共 **19 B**。
- 接收器结果：`bytes=19`，`match=True`。
- SHA-256：`524e65b90bd505fa33bb9eb91fdd24a54bceec0f638ce6067890421c33e94da9`。
- 原生界面 notice 报告移除了 **1 个控制字符**。

本轮核对了 ESC 被去除的指定样本。其它 C0/C1 字符、真实拖放、多行粘贴确认、各 shell 的 bracketed paste 行为仍须分别验证。

上述结果可在 AX 文本中读到；同时期截图可能停留在旧终端内容。因此，这两项记为**接收字节校验通过**，不记为“可见结果显示通过”。

## 4. 有限输出、Ctrl-C 与资源观察

使用有界 Perl 输出负载：循环最多 8 秒、另设 12 秒 alarm、内容上限 2.5 MiB；没有运行无限 `yes`。负载与采样仅用于受控观察，不连接外部服务器。

```sh
/usr/bin/perl -MTime::HiRes=time,sleep -e '$|=1; $SIG{INT}=sub { printf "\r\nP0_NATIVE_INTERRUPTED %.6f\r\n", time; exit 0 }; $SIG{ALRM}=sub { exit 124 }; alarm 12; my $end=time+8; my $chunk=(("x"x78)."\r\n")x64; for (1..512) { last if time >= $end; print $chunk; sleep 0.02 }; printf "\r\nP0_NATIVE_DONE %.6f\r\n", time'
```

观察结果：

- 一轮自然结束，读到 `P0_NATIVE_DONE`。
- 另一轮发送一次 Ctrl-C，读到 `P0_NATIVE_INTERRUPTED`。
- 工具动作到 AX 结果的一次观测为 **418 ms**。该区间包含工具调度和 AX 观测，未对齐真实键盘事件、前端输入、Rust 接收、PTY 信号和屏幕绘制时间点，**不能称为真实按键延迟或据此判定响应预算通过**。

资源采样：40 秒内采集主进程 PID `4229` 的 RSS，首次 **110,720 KiB**、峰值 **118,944 KiB**、末次 **118,208 KiB**。它没有包含 WebKit 辅助进程，没有逐样本标记输出/空闲等阶段，也不是物理 footprint。不能据此判定全应用内存预算、长期稳定性或泄漏与否。

原有 [性能基线](PERFORMANCE_BASELINE.zh-CN.md) 的 CLI PTY、Chrome stub 与空闲应用测量边界仍有效；本轮没有把它们相加为原生端到端性能结论。

## 5. Unicode：内容与可见字形分开记录

样本为 `中文 🌏 👨‍👩‍👧 🇨🇳 é`。原生观察如下：

| 层次 | 观察 | 尚不能证明 |
| --- | --- | --- |
| AX 文本 | 保留上述样本文本 | 视觉字形、光标宽度正确 |
| 可见输出 | 中文、地球 emoji 正常可见；家庭序列有家庭图形 | 家庭图形占列、选区和光标行为正确 |
| 旗帜 | `🇨🇳` 显示为带虚线的 C/N 字母样占位 | 尚未定位是字形回退、DOM 分段/间距还是其它绘制因素 |
| shell 编辑行 | 曾见重复 emoji 和 `<200...` 片段残留，执行后的输出字符正确 | 尚未确认该片段的完整内容、重复来源或根因 |

[输入路径报告](INPUT_PATHS.zh-CN.md) 已记录 Unicode 11 下家庭序列占 6 列、旗帜为两个宽 1 的区域指示符，以及与 shell `wcwidth` 不一致可能造成编辑错位。既有浏览器测试固定了这些缓冲单元行为，**没有证明本轮原生字形异常的原因**。本轮不修改字体、宽度提供器或 xterm 版本。

后续最小隔离可用纯 ASCII 的 `printf` 转义命令生成同一输出，避免 Unicode 粘贴命令行参与 ZLE 编辑：

```sh
printf 'A\U0001f1e8\U0001f1f3Z\n'
printf 'A\U0001f468\u200d\U0001f469\u200d\U0001f467Z\n'
```

上面是复验方法，不将其列为本文已完成的独立字节/字形验证。

## 6. 未决：AX 更新但截图中可见终端停留旧画面

后台自动化截图与前台人工操作的结果需要分开记录，不能用其中一组覆盖另一组，也不能直接推导为前台终端缺陷。

### 已观察到的现象

1. 有限高输出及 IME 操作之后，AX 继续显示后续粘贴接收校验、`printf` Unicode 等新结果，状态栏接收字节数也增长。
2. 多次 CUA 截图中的终端区域仍停留在先前 `nihao` / “你好”及旧 prompt；状态栏有更新，所以不能描述为整个窗口或整个事件循环冻结。
3. 向下滚动和 Ctrl-L 未使截图中终端内容按预期更新。
4. 切到 demo 标签再返回 Local，截图中的终端更新为 Ctrl-L 后的空白 prompt；继续输入新的 `printf`，字节数增加，截图又停在旧 prompt。
5. 新建 `Local 3`，仅执行 `printf 'P0_RENDER_1\n'`，接收计数为 **436 B**，截图中的终端仍为空白。这轮计数含会话相关输出，不是 marker 本身长度。
6. 用户手动将 `Local 3` 置前台后，确认看到 `P0_RENDER_1`；再输入 `echo P0_RENDER_2`，立即显示第二条 marker。用户直接回复“两条都能正常显示”。
7. 用户回复后，CUA 再次取得的截图与 AX 状态均显示两条命令及对应 `P0_RENDER_1`、`P0_RENDER_2` 输出，提示符正常，接收计数为 **786 B**。这次前台人工结果有工具回读支持；截图仍仅为会话工具记录，没有另行落盘。

这组对照支持继续检查前后台/可见性差异；还不能确定自动化画面停滞发生在渲染、捕获或其它环节。前台这两条 marker 的显示正常，**不能将先前“截图停滞”直接等同为用户实际屏幕冻结**；同样，两条 marker 的成功也不证明所有高输出、IME、切后台/恢复场景都没有刷新问题。

### 只读源码线索与下一步

- `main.ts` 切标签改变 pane 的 `hidden`，随后在 rAF 中执行 fit；FitAddon 仅在行列变化时触发尺寸刷新，同尺寸 fit 不保证强制重绘。
- 锁定的 xterm RenderService 用 IntersectionObserver 判断 `.xterm-screen` 可见性；不可见时暂停 renderer 并保留待全刷标志，恢复可见时请求全刷。
- xterm 可见行绘制走 rAF；AX 的 AccessibilityManager 另有 onScroll、字符事件及定时合并路径，因此 AX 更新不充分证明可见 renderer 已刷新。
- 应用终端 CSS 有 flex、圆角及 `overflow:hidden`，但未发现应用给终端设置 transform、content-visibility 或 contain。静态检查没有确认 CSS 缺陷。

先对同一终端比较 **缓冲/AX、新旧 `.xterm-rows` DOM 文本、截图/用户直接观察**；再记录元素实际矩形、hidden/display/visibility、IntersectionObserver 结果、有限 rAF 计数和 onRender 次数。若 DOM 已新而画面旧，应检查绘制/捕获层；若 DOM 可见行旧而 AX 新，再检查 renderer 调度和可见性状态。不能在缺少这些证据时宣称 IntersectionObserver、IME 或高输出是根因。

本报告不引入定时强制刷新或每块输出刷新，不以标签切换能短暂更新作为修复通过证据，也不基于未定根因的后台自动化观察进行猜测性修复。
