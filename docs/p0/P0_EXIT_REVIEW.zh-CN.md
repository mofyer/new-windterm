## 2. 剩余四类关闭条件

编号 E1–E4 仅供本评审追踪，不是新的功能基线 ID。每项至少要有设备/平台、版本、被测提交或上游包、步骤、原始结果及未覆盖范围；发现失败须保留失败与复验记录。

| 条件 | 当前缺口 | 关闭需要的证据 | 当前状态 |
| --- | --- | --- | --- |
| E1 上游实机行为与差异 | 已冻结范围主要依据 README/静态材料；影响实现语义与内核的行为尚未确认 | 按[手工清单](HANDS_ON_CHECKLIST.zh-CN.md)记录 G13 模式快捷键、F08/F09 SCP 入口、Q06 回滚上限、S08 布局恢复；继续覆盖 ADR 闸门所需的 vttest 双尺寸/边距/矩形/SIXEL、折叠/大纲/时间戳作用对象与历史容量。每个已盘点 ID 关联截图/日志、实际行为、差异结论；未覆盖 ID 明列，不能用前四项冒烟代表全量盘点完成 | 已有 A1/A3 及部分 A2/A4，见第 4 节；未关闭 |
| E2 macOS 原生输入、无障碍与性能 | 浏览器输入探针与 PTY 独立测量不能回答 WKWebView 真实体验 | 在 M 系列机器的原生窗口记录系统/输入法/构建版本；真实组字与候选窗、Enter 提交与重复输入、宽字符/emoji、粘贴完整性和注入防护、VoiceOver 焦点与朗读。持续输出测量须覆盖 PTY→IPC→xterm，记录固定负载、吞吐、输入/Ctrl-C 延迟、队列/完整性与内存峰值及结束后状态；对未测语言、规模和平台逐项标明 | 已有单轮拼音、粘贴/过滤及有限输出；显示与宽字符仍有风险；未关闭 |
| E3 真实串口风险 | 虚拟 PTY 不能证明波特率、电气行为、设备枚举与拔插 | 记录设备型号、芯片/驱动、系统、接线与回环方式；使用真实设备核对参数设置和回读、双向收发完整性、超时、拔插断开与重新枚举。无设备时保留“阻塞”，写出条件和后续处理建议，不能计通过 | 用户确认暂无设备，先做其他验收；硬件阻塞，未关闭 |
| E4 技术风险、架构与工期评审 | 终端内核 ADR 仍为提议；首版估算已落后于冻结范围及新探针证据 | 汇入 E1–E3；逐条处理 ADR 决策前验证及切换闸门，明确证据、未验证原因、适用阶段和建议。更新风险与工作量估算，完成独立评审并形成明确出口决定；无法满足的条件提交可审阅的技术调整/风险处理建议，由用户确认适用的范围或路线变更 | 待 E1–E3 结果及重估；未关闭 |

关闭 E2 需要明确“测到的数值如何影响路线”的结论。若没有预先确认的响应/内存预算，只能记录测量基线与风险建议，不能事后挑阈值宣布性能达标。无法通过自动化观察的输入法候选窗、声音朗读等，须注明未覆盖并补实测证据。

E1 的“没有找到入口”只代表指定版本、指定检查路径下未见，不能据此删除冻结 ID。需要修改验收措辞时，附证据和理由并同步三处台账；新增能力按冻结变更规则走批准流程。

## 3. 出口评审必须消除的旧假设

1. [EFFORT_ESTIMATE](EFFORT_ESTIMATE.zh-CN.md) 基于 2026-10-11 的 `d3917d8`、130 个 ID 与尚未分诊的 36 项候选；目前是 164 项冻结能力。旧文的“P0 剩余 6 / 9 / 15 人周”及完整项目数值属于历史估算，不能直接当作当前剩余工期。重估须消除候选重复计入、纳入新增 ID，并更新各阶段合计、关键路径和人员情景。
2. 旧估算中的 GSSAPI 仅 ADR、Linux/Windows 原生窗口未运行等描述已被后续有限证据更新；应降低对应不确定性，但不能把探针成本直接折算为产品交付已完成。真实串口、原生输入及性能等仍保留风险。
3. [TERMINAL_CORE_ADR](TERMINAL_CORE_ADR.zh-CN.md) 建议 H1 + H4，并列出内核切换闸门、图像插件/CSP、安全与原生验证。该文件仍为提议，本草案不将其升格为批准决定，也不自动引入插件、升级 xterm 或更换内核。
4. ADR 中依赖未来上游发布、设计接受或特定方案启用的验证，须在定稿时明确触发条件与阶段。等待上游不能成为无限延长 P0 的默认理由；需要后移的项应说明替代路线、风险和关闭条件，待评审确认，不能在本草案中自行豁免。

## 5. P1 入口与范围

P1 的正式入口仍是 [ROADMAP](../ROADMAP.zh-CN.md) 中的 **P0 通过**。进入前，须完成本评审的证据回填和独立评审，清楚记录仍存风险及经确认的处理决定；本轮没有自动准入。

P1 优先将已有原型做成稳定的本地终端：应用状态与必要的终端边界、PTY 生命周期和背压、输入法、终端兼容、屏幕/滚动历史、基础标签页和内存管理；建立可重复的原生响应与完整性预算，保留 Windows/Linux 的实现与验证路径。具体拆分以定稿 ADR 和更新估算为准。

完整 SSH/SFTP、串口产品会话、ZMODEM、全部 VT 补齐、工作流 GUI、签名公证和正式发行继续按 P1–P5 的对应工作包交付。P0 需要取得足以支撑路线的证据与风险结论，不要求提前完成这些产品功能，也不能因此删除其最终验收要求。
